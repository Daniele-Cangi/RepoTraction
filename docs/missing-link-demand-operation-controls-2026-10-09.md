## Reference fields and evidence

Each card contains historical URL, original body/acquisition hashes, saved query,
read ranges and independent root-span anchors. Raw bodies, author details and
verbatim snippets stay private; the public manifest publishes operator paraphrases
and exact span hashes/offsets. Offset and SHA agreement prove provenance, not the
meaning of a claim. The URL identifies the issue, not a newly checked live state.

| Field | Operator reference boundary |
| --- | --- |
| `requested_change` | What implementation/help outcome the root actually requests; a question must not become a chosen fix. |
| `input_shape` | Values, structures and relevant context stated in the request; generic parameter names do not establish accepted inputs. |
| `output_shape` | Requested emitted/returned behavior; transport status does not substitute for application success. |
| `runtime` | Reported execution context only where stated. It does not establish source interoperation or verify deployment. |
| `acceptance` | Stated success conditions; reported reproductions/fixes are not executions by this operator. |
| `constraints` | Separately anchored requirements, including preserving a path prefix or waiting for owner scope. |
| `context_gaps` | Missing discussion, references, actionability, source fit, novelty and adoption. |

The five fields yield **44 stated values and eleven explicit unknown values**.
Six additional constraints are stated. Their 74 anchors identify nonempty original
root spans inside the supplied read ranges. Unknown fields carry null values,
empty anchor lists and a reason; they are not blanks to fill by inference. Every
stated value has `execution_or_semantics_verified=false`: these cards describe
the root's request, not independently verified target behavior.

All eleven cards retain `demand_complete=false`, and compatibility/eligibility
are `unassessed`. This preserves missing full-discussion/adoption context while
allowing a local requested change or constraint to be recorded. Unknown runtime
must not erase educational implementation demand, and unknown acceptance must
not erase an explicit design question. Neither a known field nor an operation
label is a source compatibility verdict or permission to execute a candidate.

## Subsequent policy evaluation boundary

The next separate implementation can produce a **demand description and a query
relationship hint** from the prepared input sections, with explicit evidence and
unknowns. It must keep predictions separate from this reference manifest and
preserve native/raw output if a model is eventually used. No output repair,
reference rewriting or title-based compatibility inference is authorized here.

Assess extraction faithfulness, preserved local constraints, semantic-layer
confusions and unsupported claims individually. Report abstention/unknowns
alongside useful stated facts; mechanically valid all-unknown output is not proof
of useful triage. Passing span/shape checks is not semantic agreement. A later
comparison on these cards is development feedback, never a fresh accuracy or
Discover utility benchmark. Freeze any new policy and its evaluation protocol
separately before testing it; this preparation does not authorize model spending
or production promotion.

Source implementation evidence, target discussion and adoption/novelty review
remain separate qualification gates. A fresh repository-only comparison requires
new frozen inputs and a separately authorized budget within the original
cumulative allowance. Zero qualified leads still defers execution/isolation,
UI/key-entry work and promotion.
